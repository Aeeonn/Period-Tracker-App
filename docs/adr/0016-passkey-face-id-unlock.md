# ADR-0016: Optional Face ID unlock with a passkey PRF wrap

- **Status:** Accepted (owner approved building `p2-passkey-unlock` early, 2026-11-14)
- **Context:**
  - SR-03 ([security-privacy.md §3](../plan/security-privacy.md#3-encryption-design)) plans optional Face ID through a WebAuthn passkey with the PRF extension. FB-07 passed on a real iPhone ([device report](../feasibility/device-report.md)).
  - The owner found typing the passphrase on every unlock tiresome while testing and asked for Face ID now, ahead of the P1 gate and before the final domain is fixed. The owner chose Face ID, not a lock-free preview, as the way to reduce passphrase prompts.
  - `LockService` ([ADR-0010](0010-lock-service-key-lifecycle.md)) already accepted `{ kind: 'passkey_prf', prfOutput }` and the crypto layer already derives `KEK_prf` (HKDF-SHA-256, info `lmk/passkey-prf/v1`), but nothing could add or remove a passkey wrap.
  - The "Lock after inactivity" setting was saved in the encrypted profile but never used: the app always locked after 60 seconds hidden.
- **Decision:**
  - **Contract (additive, `CONTRACTS_VERSION` stays 1).** `LockService` gains:
    - `passkeyInfo()` → `{ credentialId, prfSalt }` (base64url) or `undefined`. Works while locked, because the lock screen needs it to start the Face ID prompt. Neither value is secret.
    - `enablePasskey(authorization, { credentialId, prfSalt, prfOutput })` → `ok` or `locked | wrong_secret | invalid_enrollment`. It needs an unlocked session and re-authentication with an existing unlock secret, like `changePassphrase`. It validates the enrollment (credential ID 1–1023 bytes, 32-byte PRF salt, 32-byte PRF output) before any key work.
    - `disablePasskey()` → `ok` or `locked`. No re-authentication: removing an unlock method cannot expose data.
  - **Storage.** The lock configuration (still `version: 1`) gains an optional `passkey` field: `credentialId`, `prfSalt` (32 bytes, the PRF input), `salt` (16-byte HKDF salt) and the LMK wrapped under `KEK_prf`. The PRF output itself is never stored. A malformed field is never used, so a corrupted wrap fails closed for Face ID (see "Damaged wrap" below for what happens to the other unlock methods). Enabling again replaces the old wrap.
  - **Serialised updates.** Every lock-configuration write (`changePassphrase`, `enablePasskey`, `disablePasskey`) applies its change to the latest committed configuration through one serialised queue, so a passphrase change and a Face ID change at the same time both survive.
  - **Unlock.** A PRF output that fails to unwrap returns `wrong_secret`; `unsupported` means no passkey wrap is stored. The passphrase and recovery code always keep working.
  - **WebAuthn wrapper** (`src/lock/passkey/`): a platform passkey (`authenticatorAttachment: 'platform'`, `residentKey: 'required'`, `userVerification: 'required'`) with the PRF extension. The relying-party ID is the page's hostname. If `create` returns no PRF result, one `get` with the same salt follows. Results map to `cancelled | unsupported | failed`, and no raw browser error is kept. A passkey that was created but cannot be used is reported to the platform with `PublicKeyCredential.signalUnknownCredential` where it exists (best effort). Callers zero PRF output buffers after use.
  - **UI.** The lock screen shows "Unlock with Face ID" only when a wrap is stored and a platform authenticator is available. The prompt starts directly from the tap, because Safari requires a user gesture. Cancelling or failing keeps the passphrase form (T-SEC-07). Settings has a Face ID card: turn on (passphrase first, then the Face ID prompt), turn off, or an explanation when Face ID is unavailable. The card is hidden in the unlocked development preview.
  - **Lock after.** Auto-lock reads its timeout each time the app is hidden. The runtime applies the saved `lockTimeoutSec` after unlock and when Settings saves it. Only the offered values (0, 60, 300, 900 s) are accepted; anything else keeps the current timeout. The default for new profiles is 60 s, as T3 specifies (it was 300 s). Cold start still always locks.
- **Consequences:**
  - **Domain-bound.** A passkey belongs to the exact hostname. Each preview alias, and later the production domain, needs its own Face ID setup. Moving domains also moves the local data (another origin), so nothing extra is lost. This replaces the earlier rule that passkeys are offered only after the domain is fixed.
  - **Passcode fallback.** iOS may accept the device passcode when Face ID fails, so anyone who knows the iPhone passcode can unlock Flo once Face ID is on. Settings states this.
  - **Delete All** erases the passkey wrap with the rest of the lock configuration. The passkey itself may stay in iCloud Keychain; without the wrap it unlocks nothing.
  - **Damaged wrap (amended 2026-11-16).** A stored `passkey` field that fails validation is now ignored instead of making the whole lock configuration invalid. The passkey method still fails closed (no Face ID offer, and no PRF output unwraps anything), while the passphrase and recovery code keep working. The next configuration write drops the damaged field. A damaged passphrase or recovery wrap is still refused.
  - **Evidence limits.** Unit tests and WebKit E2E use a synthetic WebAuthn stub (Playwright WebKit has no virtual authenticator). Real Face ID enrolment and unlock, including offline and after restore, are proved only by a real-iPhone check.
